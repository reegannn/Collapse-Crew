# Game design across all milestones

The design that every milestone plan relies on. Read this before any single plan. It
fixes the things that must be consistent everywhere: how the world is laid out, what the
rules of a run are, which modules exist and in what order they load, every network
message, every saved field.

Nothing here has been run. All numbers are first guesses to be tuned in M12.

## 1. The player journey

1. **Join.** The player appears in the lobby. Their saved data loads; coins show on the
   leaderboard. A first-time player is sent straight into a 90-second solo tutorial (M9).
2. **Form a team.** The lobby has **launch pads**. Standing on a pad puts you in that
   pad's team (up to 4). A console on the pad has a "Ready" prompt. When everyone on the
   pad is ready, a short countdown runs.
3. **Launch.** The team is moved to a private **arena**: a copy of a location, built far
   away from everyone else.
4. **Escape.** A short briefing, then the hazard starts rising. The team clears rooms by
   solving a teamwork puzzle in each. Each solved room opens the gate to the next.
5. **Finish.** Everyone still in the run reaches the exit at the top: success. Everyone
   is caught, or time runs out: failure. Either way a results screen shows coins and XP.
6. **Return.** Back to the lobby. Spend coins on cosmetics and camp upgrades. Come back
   tomorrow for the Daily Expedition, the daily reward and the streak.

No custom on-screen interface is needed to play before M9: joining, readying and every
puzzle interaction use the physical world and Roblox's built-in prompts, which already
work on phone, keyboard and gamepad. M9 adds the interface on top.

## 2. World layout

Everything is generated by code from data. Nothing is hand-placed in Studio in this
phase. The code must not depend on anything already in the place file (baseplate,
default spawn): every spawn and teleport is done explicitly.

```
        Y up
        |            LOBBY                              ARENAS (one per team in a run)
        |      origin (0, 100, 0)                 slot 0            slot 1            slot 2 ...
        |   ┌───────────────────────┐          (0,100,4000)    (2500,100,4000)   (5000,100,4000)
        |   │ camps  [pads x4]      │               │                 │                 │
        |   │        spawn ring     │          each slot holds one generated location
        |   └───────────────────────┘
        └──────────────────────────────────────────────────────────────> X      (Z: lobby 0, arenas 4000)
```

- **Lobby**: a 160 x 160 platform with rails. Spawn points on a ring. Launch pads along
  one edge. Camp plots around the rim (M8).
- **Arenas**: `ArenaConfig.slotCount` slots (6), 2500 studs apart, so teams never see or
  hear each other and Roblox's streaming never mixes them.
- **Inside an arena, a location is a climb.** Rooms are boxes stepped upward like a
  staircase. Local axes: `+Y` up, `+Z` is the direction of progress, `X` is sideways.

```
   side view (Z ->, Y up)                                          ┌─ exit platform
                                                    ┌──────────┐ ╱
                                        ┌─────────┐ │  Room 3  │╱  ramp
                            ┌─────────┐╱│  Room 2 │╱└──────────┘
                            │  Room 1 │ └─────────┘
                            └─────────┘
   ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~  hazard surface, rising
```

- Each room has an **entry doorway** (on its `-Z` wall) and an **exit doorway** (on its
  `+Z` wall). The exit doorway is blocked by a **gate** that the room's puzzle opens.
- Past each gate is a short flat landing, then a **ramp** up to the next room.
- The **hazard** is one large flat slab under the whole location that rises. Lower rooms
  flood first.
- The **exit platform** sits above the last room. Its top is above the hazard's final
  height, so reaching it is always safe.

## 3. A run, phase by phase

The round state machine (M4). `Success` and `Failure` are the two endings.

| Phase | What happens | Ends when |
|-------|--------------|-----------|
| `Lobby` | Not in a run. Also the "finished, cleaned up" state. | A team launches |
| `Briefing` | Team is in the first room. Objective shown. Hazard not moving. | `briefingSeconds` pass |
| `Running` | Clock runs, hazard rises, puzzles are live. | Win, lose, or everyone leaves |
| `Success` / `Failure` | A short beat for the outcome. Hazard stops. | `outcomeSeconds` pass |
| `Results` | Rewards are granted and shown. | `resultsSeconds` pass |
| back to `Lobby` | Players return to the lobby; the arena is destroyed. | - |

## 4. Rules of a run

- **Caught.** A player is "caught" when the hazard has covered them for the hazard's
  grace time (water: waist deep for 2 seconds; lava: any touch). Dying any other way
  (falling, reset) counts the same.
- **Respawn or out.** A caught player returns to the **current room's checkpoint**,
  with a few seconds of protection, **if that checkpoint is still above the hazard**.
  If the checkpoint is flooded, the player is **eliminated**: they are moved to a safe
  spectator ledge and watch the rest of the run.
- **Win.** Every player who is still active (not eliminated, not left) is standing in
  the exit zone at the same moment.
- **Lose.** No active players remain (`AllCaught`), or the clock runs out (`TimeUp`).
- **Checkpoints advance** when a room's puzzle is solved: the next room's checkpoint
  becomes the respawn point.
- **Fairness when the team shrinks.** Puzzles scale to the number of **active** players
  and only ever get easier mid-room (a helper crate appears, a timer lengthens), so a
  team is never left with a puzzle it cannot physically finish.
- **No joining a run in progress** in v1. No reviving in v1 (roadmap R4).

## 5. Teams

- A team forms on a pad. **Membership is physical: you are in the team while you stand
  on its pad.** Stepping off leaves it. (Network messages for "join" and "quick play"
  simply move the player onto a pad; the same single rule then applies.)
- Team size 1 to 4. Solo is allowed (flag `SoloPlayAllowed`).
- Team phases: `Forming` -> `Countdown` -> `Launching` -> `InRun`. Once `Launching`,
  membership is locked and the pad is freed for the next team.
- Any change (someone joins, leaves, un-readies) cancels a countdown.
- A player who disconnects is removed in any phase. If a team in a run becomes empty,
  the run is abandoned and cleaned up.
- If no arena is free, a launching team waits in a first-come queue.
- Pad modes: `Standard` (M3), `Daily` (M8), `Tutorial` (M9).

Notes:

- **Puzzle and lobby interactions send no remotes at all.** They use `ProximityPrompt`,
  whose `Triggered` event fires on the server with the player. The server still
  validates distance and state itself (`Puzzles/Interaction`).
- **Fast-changing values are not sent as messages.** Hazard height and progress are
  written to attributes on the arena folder (section 10), which Roblox replicates.
- Deadlines sent to clients (`phaseEndsAt`, `countdownEndsAt`) are `Time.SyncedNow()`
  values, so each client counts down locally without per-second messages.
- A `Function` handler always returns `(ok: boolean, payload)`; on failure `payload` is
  a short reason code such as `"NotEnoughCoins"`.

## 12. Player save data

The shape saved for each player (`Types.PlayerData`), as it will be at launch. M2
creates the template with the M1 fields; later milestones add the fields marked with
their milestone.

```lua
{
    schemaVersion = 1,
    firstJoinAt = 0,            -- unix seconds; 0 until first set
    lastSeenAt = 0,
    coins = 0,
    xp = 0,                     -- lifetime XP
    level = 1,
    streak = {
        current = 0, best = 0,
        lastPlayedDay = 0,      -- UTC day number; 0 = never
        lastDailyRewardDay = 0,
        milestonesClaimed = {}, -- M8: milestone id -> true, cleared when the streak resets
    },
    ownedCosmetics = {},        -- cosmetic id -> true
    equippedCosmetics = {},     -- slot -> cosmetic id
    campUpgrades = {},          -- upgrade id -> level
    receipts = {},              -- purchase id -> unix time granted (capped, M7)
    settings = { reducedMotion = false, musicVolume = 0.7, sfxVolume = 1 },
    stats = { runsStarted = 0, runsCompleted = 0, roomsCleared = 0 },
    tutorialCompleted = false,
    firstClears = {},           -- M7: location id -> true
    daily = { lastClearDay = 0 }, -- M8: last day the Daily Expedition bonus was granted
}
```

**How the shape may change (the migration rule):**

- **Adding a field with a default** needs no migration and no version bump. Add it to
  `ProfileTemplate` and `Types.PlayerData`; `TableUtil.Reconcile` fills it into older
  saves on load.
- **Renaming, removing or changing the meaning of a field** needs `schemaVersion + 1`
  and a migration function in `Data/Migrations`.
- Only plain data is saved: numbers, strings, booleans, lists, string-keyed
  dictionaries. Never an Instance, Vector3, Color3, NaN or infinity.

## 13. Player-facing text

All text a player reads comes from `Shared/Strings.luau` (M2) by key, so localisation
later is a table swap. Keys are dotted: `Notice.DataSafeMode.Title`,
`Objective.HoldTheDoor.PullLever`, `Shop.Item.Trail_Blue.Name`. `Strings.Get(key, ...)`
formats with the extra arguments and returns the key itself (with one warning) when a
key is missing, so a typo is visible on screen instead of crashing.

Server-built world text (pad billboards, prompt labels) uses the same table.

There is **no player-typed text anywhere in v1** (no custom chat, no naming things), so
there is nothing to filter. Display names come from Roblox, already moderated. If
player-typed text is ever added it must go through `TextService` filtering first.

## 15. Patterns to follow

**Writing a service.** Copy the shape of `PlayerSessionService`: header comment
(purpose, public API, contract); requires; module-level state; private functions;
`Init()` (own state and signals only, no yielding, no calls to other services);
`Start()` (connect remote handlers first, then signals of services above, then loops).
Signals are public fields created at module level
(`Service.Changed = Signal.new() :: Signal.Signal<...>`).

**Per-player state.** Key tables by `Player`. Create the entry when the player is
ready for it, and **always** delete it in a `Players.PlayerRemoving` handler. Before
storing anything for a player after a yield, check `player.Parent ~= nil`.

**Adding a remote.** Add the definition (section 9) -> connect exactly one server
handler in a `Start()` -> add a row to the remotes table in `ARCHITECTURE.md`. Client
handlers validate nothing themselves; server handlers re-check every rule (does the
player own it, can they afford it, are they in the right state) because the schema only
proves the *shape* of the arguments.

**Loops.** One loop per system, not per player or per object. Fixed tick from Config
(`RoundConfig.tickSeconds`, `LobbyConfig.Pad.checkIntervalSeconds`). Wrap each item's
work in `pcall`/`xpcall` so one bad round or player cannot stop the loop.

**"Is this player inside this box?"** Use maths, not touch events:
`ZoneUtil.Contains(zone, position)` converts the position into the box's own space and
compares with half its size. `Touched` events are unreliable and can be faked.

**Moving a player.** Always through `World/Teleport.ToCFrame(player, cframe)`. It
handles a missing character, sitting, streaming and leftover velocity.

**Trusting a player's interaction.** Always through `Puzzles/Interaction` (M6): is the
player an active member of this round, alive, close enough, and not spamming?

**Changing saved data.** Only through `DataService.Update(player, reason, mutator)`.
The mutator must not yield. Coins only through `EconomyService`; XP only through
`ProgressionService`.

**Check-then-change must not yield in between.** Luau runs one thing at a time, so
"check the player can afford it, then take the coins" is safe **only if nothing pauses
between the check and the change**. This single rule is what makes rewards and
purchases impossible to double-claim.

## 16. Roblox pitfalls to design around

- **Circular requires** between services error at load. Follow the load-order rule.
- **`UpdateAsync` transform functions must not yield** and may run more than once.
- **Teleporting a character the instant it spawns** can be undone by the engine's own
  spawn placement. Wait for the root part, then defer one step. Mark with a TODO.
- **`player.Character` can be nil** at any time (respawning, leaving). Every use checks.
- **Carried objects welded to a character are physically owned by that player's
  device**, so their position can be faked. Never trust a carried object's position;
  use the (plausibility-checked) player position instead. Objects not being carried are
  anchored, which the server fully controls.
- **Streaming**: with `StreamingEnabled`, parts far from a player do not exist on that
  player's device. Client code must tolerate missing arena parts. Server code is
  unaffected. Ask the engine to stream the destination before teleporting.
- **Tables sent over the network or saved** must be lists or string-keyed dictionaries
  (decision D-012).
- **Signal timing**: Roblox can deliver events immediately or deferred, depending on a
  place setting. Never rely on a handler having run "by the next line".
- **Humanoid properties** set by the server (walk speed) can be changed locally by a
  cheater. Speed is enforced by server-side plausibility checks (M11), not by trusting
  `WalkSpeed`.
- **Set an instance's properties before parenting it** to `workspace`, so clients
  receive it in its finished state.
